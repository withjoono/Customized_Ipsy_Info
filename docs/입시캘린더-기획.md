# 입시 캘린더 — 기획서

> Infocast(맞춤 입시정보 배달앱) 신규 화면. 작성일 2026-08-20.
> 전제: 데이터 소스는 **기존 `ic_info_item` 재활용**(신규 테이블 없음), 대시보드에서는 **D-day 히어로 + 미니 캘린더**를 최상단 주요 섹션으로 배치.

---

## 0. 왜 캘린더인가

이 앱의 콘텐츠는 대부분 **시간이 핵심**이다. `InfoCategory` 7종 중 `SCHEDULE`(원서접수/전형 일정), `DEADLINE`(마감 임박), `BRIEFING`(설명회), `GUIDELINE_CHANGE`(모집요강 변경)은 전부 "언제"가 정보의 절반이다. 그런데 현재 UI는 관련도순 피드 하나뿐이라 사용자가 **"내가 이번 주에 놓치면 안 되는 게 뭐지?"** 에 답할 수 없다.

푸시(배달)는 *그 순간*만 알려주고 사라진다. 캘린더는 그 배달물을 **시간축에 쌓아 보여주는 영구 뷰**다. 즉 캘린더는 새 기능이 아니라 **기존 배달 엔진의 두 번째 출력 포맷**이다.

경쟁 서비스 리서치(§1) 결과, 국내 입시 서비스는 대부분 캘린더를 갖고 있지만 전부 **전 국민 공통 일정**만 보여준다. 우리는 Hub 입시 프로파일 + 구독 태그가 있으므로 **"내 일정만 남긴 캘린더"** 라는 차별점을 가진다. 이것이 이 화면의 핵심 포지셔닝이다.

## 1. 레퍼런스 리서치 (웹 조사)

| 서비스 | 캘린더 형태 | 개인화 | 배울 점 / 안 할 점 |
|---|---|---|---|
| **어디가(adiga.kr)** — 대교협 공식 대입정보포털 | 대입일정/대입뉴스 중심, 공식 일정 원천 | 없음 | **일정의 신뢰 원천으로 사용**. 우리 캘린더의 "공식" 배지는 여기/대교협·평가원 기준 |
| **진학사 입시 캘린더** | 월 그리드 + **달력/목록 2뷰 토글**, 연·월 이동 | 없음 | **2뷰 토글은 그대로 차용**(모바일=목록, 데스크톱=달력). 정보 밀도 조절의 핵심 |
| **메가스터디 / 유웨이 / 내신닷컴** | 학년도별 정적 일정표(PDF·팝업) | 없음 | 학년도 전체를 한 장에 보는 "연간 조망" 수요 확인 → **연간 타임라인은 Phase 2** |
| **나무위키 수능 D-day 틀 / D-day 계산기 앱** | D-day 숫자 하나 | 없음 | **D-day 숫자 자체가 가장 소비되는 단위**. 캘린더보다 D-day가 먼저다 → 히어로 채택 근거 |

**리서치 결론 3가지**

1. **D-day가 캘린더보다 먼저 소비된다.** 달력 격자를 먼저 보여주는 서비스는 많지만 사용자가 실제로 확인하는 건 "수능 D-91" 같은 숫자 하나다. → 대시보드 최상단은 **달력이 아니라 D-day 히어로**, 미니 달력은 그 보조.
2. **달력/목록 토글은 필수.** 모바일에서 월 그리드는 셀당 1~2줄밖에 못 넣는다. 진학사도 2뷰를 쓴다.
3. **아무도 개인화를 안 한다.** 전 서비스가 동일한 공통 일정표. 우리만 "내 전형·내 지역·내 학년" 필터가 가능 → **기본값을 "내 일정"으로 두고 "전체"를 토글**로 두는 것이 유일한 차별점.

## 1.3 관심 대학 필터 (`universities` 태그 차원 신설)

대학별 일정을 개인화하려면 태그 체계에 대학 축이 필요해 다음을 추가했다.

| 파일 | 변경 |
|---|---|
| `tags/tag.types.ts` | `TagSet.universities` 추가. 화이트리스트 없는 자유 문자열(신설·개명 대학 대응) |
| `tags/tag.normalizer.ts` | 공백 제거 정규화(`차 의과학대` → `차의과학대`), 최대 200개·40자 제한 |
| `tags/tag.match.ts` | 매칭 차원 추가 + **가중치 4** (전형 3, 계열 3, 학년 2, 지역 1보다 높음) |
| `match.service.ts` | 구독의 `interests.universities` 를 질의에 반영, 매칭 사유 `관심 대학` |
| `subscription.service.ts` | 관심사에 `universities` 저장 |
| `subscribe.tsx` | 관심 대학 검색·선택 UI (98개교 자동완성) |

매칭 규칙은 기존과 동일하다 — **질의가 비어 있거나 아이템 태그가 비어 있으면 통과**. 따라서 관심 대학을 고르지 않은 사용자에게도 대학별 일정이 보이고, 전체 일정은 관심 대학과 무관하게 항상 보인다. 관심 대학을 고르면 그 대학 일정의 점수가 크게 올라 캘린더·피드 상단에 배치된다.

## 1.4 공개 일정 페이지 `/schedule` (로그인 불필요)

공유·검색 유입용. 개인화 없이 **전체 일정을 날짜별로 묶어** 보여준다.

- 백엔드: `GET /api/public/calendar?from=&to=&q=` — **인증 가드 없음**. 승인된 일정만, 날짜 오름차순, 최대 1000건. `q`는 대학명·제목 부분일치(공백 무시).
- 프런트: `/schedule` — 히어로(가장 가까운 일정 D-day) → 대학명 검색 → 카테고리 칩 + 지난 일정 숨기기 → 월/날짜별 목록.
- 로그인 사용자에게는 "내 맞춤 캘린더로 →" 링크를 노출해 `/calendar` 로 연결한다.
- 날짜별 목록 컴포넌트(`ScheduleByDate`)는 캘린더 페이지의 '목록' 뷰와 공용이다.

> 공개 엔드포인트에는 개인정보가 절대 실리지 않아야 한다. 응답은 일정 필드와 `universities` 태그만 내려준다.

## 1.5 학년별 화면 분기 (고1 ~ 재수생)

대상이 고1~재수생 전체이므로 **모두에게 같은 화면을 주면 안 된다.** 캘린더의 의미가 집단마다 다르다.

| 대상 | 캘린더의 성격 | 히어로 |
|---|---|---|
| 고1 | 준비 리듬 | **준비 모드** — "지금은 내신·과목 선택의 시기". D-day 카운트다운 없음 |
| 고2 | 예열 | **준비 모드** — "1년 뒤 이 시기에 원서를 씁니다" |
| 고3 | 실행 | **실행 모드** — 가장 임박한 일정 D-day |
| 재수생(`N`) | 실행, 다른 경로 | 실행 모드 + "재학생과 접수 창구가 다릅니다" 안내 |
| 미상(null) | — | 실행 모드 기본형 (Hub 장애 시 폴백) |

**왜 고1·고2에게 D-day를 안 보여주나** — 1년 반 남은 수능에 D-456을 띄우는 것은 실행 가치가 없고 불안만 키운다. 내 일정이 아닌 것의 카운트다운 나열(`hero__next`)도 준비 모드에서는 숨긴다.

### 재수생 지원 — `Grade`에 `'N'` 추가

기존 `Grade = 1 | 2 | 3` 에는 재수생이 들어갈 자리가 없었다. 대학별 면접·발표 345건에 `grades: [3]` 을 달면 **정작 올해 지원하는 재수생 피드에서 해당 일정이 전부 사라진다**(매칭 규칙상 교집합 없음 → 탈락).

| 파일 | 변경 |
|---|---|
| `tag.types.ts` | `Grade = 1 \| 2 \| 3 \| 'N'`, `APPLICANT_GRADES = [3, 'N']` |
| `tag.normalizer.ts` | 재수생 별칭 흡수(`N`, `재수생`, `졸업생`, `검정고시`, `0`, `4` …) |
| `match.service.ts` | Hub `grade` 값을 TagNormalizer로 정규화해 질의에 사용 |
| `profile/` (신규) | `GET /api/profile/me` → `{ grade, curriculum }`. **학년/교육과정만** 노출(성적·생기부 등 민감 필드 제외) |
| `useProfile.ts` | 프런트 학년 훅 + `isApplicant()` / `isUnderclassman()` |

> **미결정 — Hub 규약**: Hub 입시 프로파일이 재수생을 어떤 값으로 내려주는지 아직 정해지지 않았다(`grade: 4`? `0`? 별도 필드?). 현재는 흔한 표현을 모두 `'N'`으로 흡수하는 관대한 정규화로 대응한다. **Hub와 규약을 확정하면 `REPEATER_ALIASES` 목록을 좁힐 것.**

### 학년 태깅 원칙

## 1.6 학년은 아이디에서 파생한다 (`26h3`)

학생 아이디에 학년이 들어 있다 — **`26h3` = 2026학년도에 고3**. 아이디는 고정이고 해가 바뀌면 자동으로 나이를 먹는다.

| 입력 | 2026-08-20 기준 | 2027-03-02 기준 |
|---|---|---|
| `26h1` | 고1 | 고2 |
| `26h3` | 고3 | **재수생** |
| `25h3` | **재수생** | 삼수생(→ `'N'`) |
| `26h4` | 재수생(전용 표기) | 재수생 |

- 구현: `src/auth/grade-from-id.ts` — `parseGradeFromId()` / `parseGradeFromClaims()`
- **학년도 경계는 3월.** 2027년 1월의 `26h3` 은 아직 고3(정시 응시 중)이고, 3월부터 재수생이 된다. KST 기준으로 판정한다.
- `h4` 이상은 재수생 전용 표기로 본다(정확한 표기 미확정 — 확인되면 좁힐 것).
- 패턴 탐색은 `sub`·`loginId`·`userId`·`username`·`studentId`·이메일 로컬파트 순. `26h3001` 같은 학번도 인식하고, `2026h3` 처럼 4자리 연도를 쓴 값은 오탐하지 않는다.
- **우선순위: 아이디 > Hub 프로파일.** Hub 의 `grade: number` 로는 재수생을 표현할 수 없고, 아이디에는 학년도 정보까지 들어 있어 더 정확하다. Hub 장애 시에도 학년을 알 수 있다.
- 검증: 22개 단위 테스트(경계 3월, 코호트 승급, 오탐 방지, 클레임 스캔).

## 1.7 시험 일정 데이터 (14건) — 출처별 신뢰도가 다르다

`infocast-backend/prisma/seed/exam-2027.json`. **항목마다 `source`/`url` 이 다르다** — 근거의 급이 다르기 때문이다. 시드 스크립트는 항목 출처를 파일 출처보다 우선한다.

**공식 확인 (서울시교육청·교육지원청 공고, 정책브리핑)**

| 날짜 | 일정 | 대상 |
|---|---|---|
| 2026-08-20 ~ 09-03 | 수능 응시원서 온라인 사전입력 | 고3·재수생 |
| 2026-08-24(월) ~ 09-04(금) | **수능 응시원서 접수** (09:00~17:00, 토·공휴일 제외) | 고3·재수생 |
| 2026-06-04(목) / 09-02(수) | 평가원 6월 / 9월 모의평가 | 고3·재수생 |
| 2026-07-01(수) / 09-29(화) | 6월 / 9월 모평 성적 통지 | 고3·재수생 |

> **재수생 접수처(공식)** — 출신 고등학교 접수가 원칙. 주민등록 주소지가 다른 시험지구면 주소지 관할 교육지원청에서 접수 가능. 검정고시 출신 등은 주소지 관할 시험지구 교육지원청. 이 내용은 재수생 히어로에 그대로 노출한다.

**시행 일정(안) 근거 — 재확인 필요 (사설 언론이 인용한 교육청 계획안)**

| 날짜 | 일정 | 대상 |
|---|---|---|
| 2026-03-24(화) | 3월 학력평가 (서울) | 고1·고2·고3 |
| 2026-05-07(목) | 5월 학력평가 (경기) | 고3 |
| 2026-06-04(목) | 6월 학력평가 (부산) | 고1·고2 |
| 2026-07-08(수) | 7월 학력평가 (인천) | 고3 |
| 2026-09-02(수) | 9월 학력평가 (인천) | 고1·고2 |
| 2026-10-20(화) | 10월 학력평가 (서울 / 경기) | 고3 / 고1·고2 |

이 항목들은 본문에 "시행 일정(안) 기준이며 공식 공고 원문은 확인하지 못했습니다. 학교 가정통신문으로 재확인하세요"를 붙였고, `source` 에도 '(안) — 언론 인용'을 그대로 표기해 화면에 노출한다.

**중요한 정정** — 고1·고2의 11월 학평 회차는 **없다.** 2026년 시행 계획은 고3 6회 / 고1·고2 4회이고, 고1·고2의 마지막 회차는 10월 20일이다. 6월 4일과 9월 2일은 고3(평가원 모평)과 고1·고2(학평)가 같은 날 **다른 시험**을 치른다.

**접근 못 한 출처** — 평가원(suneung.re.kr)·교육부(moe.go.kr)는 robots.txt 로 차단되어 원문을 읽을 수 없었다. 교육청 공고 첨부는 대부분 HWP/PDF 바이너리다. 모평 일정은 서울시교육청 산하 공식 공지로 대체 확인했다.

### 준비 모드 판정을 학년이 아니라 '내 일정 유무'로 바꿨다

학력평가가 들어오면서 **고1·고2에게도 자기 D-day가 생겼다**(9월 학평 D-13). 준비 모드를 학년으로 판정하면 이 D-day를 못 보여준다. 그래서 판정 기준을 바꿨다.

```
내 학년이 명시적으로 대상인 일정(매칭 사유 '학년 일치')이 있으면 → 실행 모드(그 일정의 D-day)
고1·고2인데 그런 일정이 없으면 → 준비 모드
```

D-day를 숨기는 이유는 "고1·고2라서"가 아니라 **"내 일정이 아닌 것을 카운트다운하지 않기 위해서"** 다.

**검증** — 고1·고2 33건 / 고3 46건 / 재수생 41건(관심 대학 '고려대' 설정 기준). 히어로: 고1·고2 = 9월 학평 D-13, 고3·재수생 = 수능 원서 사전입력 D-DAY(2026-08-20).

## 1.8 학교 학사일정 — Hub NEIS 모듈을 소비한다

고2 이하에게는 중간·기말고사가 사실상 가장 중요한 D-day다. 그런데 학교 일정은 **사용자마다 다르다.**

**NEIS 를 우리가 직접 붙이지 않는다.** Hub 에 이미 NEIS 모듈이 있고(`Hub-Backend/src/modules/neis`), 학교 연동·Redis 24h 캐시·정규화까지 되어 있다. 생기부·모의고사와 같은 원칙 — 소스는 Hub 만 소비한다.

### Hub 계약 (확인 완료)

| 엔드포인트 | 인증 | 용도 |
|---|---|---|
| `GET {HUB}/neis/schedule?year=&month=` | **사용자 JWT** | 내 학교 학사일정(프로필에서 학교코드 자동 조회). 위성앱용 경로 |
| `GET {HUB}/neis/my-school` | 사용자 JWT | 연동된 학교 정보 |
| `POST {HUB}/neis/my-school` | 사용자 JWT | 학교 연동 |
| `GET {HUB}/neis/schools?q=` | 공개 | 학교 검색 |

응답: `{ date: 'YYYYMMDD', eventName: string, isHoliday: boolean }[]` · 학교 미연동이면 **404**.

> **서비스 인증이 아니라 사용자 JWT** 다. 우리 백엔드가 쓰던 `/api/internal/...` (ServiceAuth) 와 경로·인증이 다르므로, 호출자의 Bearer 토큰을 그대로 전달한다.

### 우리 쪽 구현

`GET /api/calendar/school?year=&month=` (`src/school/`) — Hub 를 프록시하며 다음을 한다.

| 처리 | 내용 |
|---|---|
| 날짜 | `YYYYMMDD` → `YYYY-MM-DD` (KST 그대로) |
| 분류 | `SCHOOL_EXAM`(중간·기말·지필·고사·평가) / `SCHOOL_HOLIDAY`(방학·휴업·공휴일·재량·개교기념) / `SCHOOL_EVENT`(나머지) |
| 학년 | 행사명의 '3학년', '고2' 표기를 읽어 대상 학년 추출. **Hub 가 NEIS 의 `ONE~SIX_GRADE_EVENT_YN` 을 버리고 있어 이름으로만 판별 가능하다** |
| 미연동 | Hub 404 → `{ linked:false, events:[] }` 로 부드럽게 (화면이 깨지지 않는다) |
| 캐시 | 하지 않는다 — Hub 가 이미 24h 캐시한다 |

프런트는 `useSchoolEvents(yms, grade)` 로 여러 달을 한 번에 받는다(히어로가 다음 달 시험까지 봐야 함).

### 캘린더는 3계층

1. **공용 입시 일정** — `ic_info_item` 파생 (389건)
2. **내 학교 일정** — Hub NEIS (사용자별, DB 저장 안 함)
3. 내 개인 일정 — 직접 추가 (미구현)

**학교 일정을 `ic_info_item` 에 넣지 않는 이유** — 거긴 모두가 공유하는 콘텐츠 테이블이다. 2,400개 학교의 일정을 부으면 오염되고, 매칭 엔진이 감당할 수 없다. 조회 시점에 합친다.

### 표시 정책

- 캘린더 페이지에 **학교 일정 레이어 토글**: `시험만`(기본) / `전체` / `끄기`. 방학·체험학습까지 켜면 입시 일정이 묻힌다.
- 카테고리 칩(입시 7종)은 학교 일정에 적용되지 않는다 — 축이 다르므로 레이어 토글이 따로 있다.
- 색 네임스페이스 분리: `SCHOOL_EXAM`(적색)·`SCHOOL_EVENT`(청록)·`SCHOOL_HOLIDAY`(회색).
- 히어로: 학교 시험은 **언제나 '내 것'**(`own: true`)이라 고1·고2의 D-day 후보가 된다.
- 미연동 시 고1·고2 히어로에 "학교를 연동하면 중간·기말고사가 들어옵니다" 안내(모드 무관).

**검증** — 18개 단위 테스트(분류·날짜변환·학년파싱·404 미연동·500 장애·학교명 조회 실패 폴백) + 렌더 확인(레이어 토글 3단, 색 구분, 상세 패널).

### 주의 — Hub 라우트의 `h` 와 학생 아이디의 `h` 는 다른 체계다

Hub 프론트(`use-grade-store.ts`)의 라우트는 `/h1`=예비고1, `/h2`=고1, `/h3`=고2, `/h4`=N수생, 고3은 `/j` 다.
반면 **학생 아이디의 `26h3` 은 고3**이다(확인 완료). 헷갈리면 전 사용자의 학년이 한 칸씩 어긋난다.

## 1.10 서버 기간 필터 — §5.1 예고한 임계를 넘었다

일정이 **580건**(전체 30 + 면접 393 + 발표 143 + 시험 14)이 되면서, 기획서 §5.1에서 "300건 넘으면 도입"이라 적어 둔 서버 필터가 실제로 필요해졌다.

**넘기지 않았으면 생겼을 일** — 프런트가 `/info-items?take=200` 으로 받아 클라이언트에서 거르고 있었다. 580건 중 200건만 와서 **나머지가 조용히 사라진다.** 개인 피드도 `/matches/me` 기본 `take=50`, 서버 내부 후보 풀 `take:300` 에 걸려 이중으로 잘렸다.

| 변경 | 내용 |
|---|---|
| `QueryInfoItemDto` | `from`·`to`(ISO), `hasDeadline` 추가. `take` 상한 200 → 2000 |
| `InfoItemService.findAll` | 기간·마감일 필터를 **DB `where` 로** 처리. 기간 조회면 `deadlineAt asc`, 아니면 기존 `createdAt desc` |
| `MatchService` | 후보 풀 `take: 300` → `CANDIDATE_POOL = 2000` |
| `useCalendarEvents` | 지난 6개월 ~ 앞으로 15개월 창을 `from`/`to` 로 지정하고 `take=1000`. `toISOString()` 은 KST 기준 하루가 밀리므로 로컬 연·월·일로 포맷 |

**검증** — 580건을 실제로 물려 렌더: 10월 전체 28일에 일정 표시, 관심 대학(고려대·성균관대) + 관심 지역(서울) 필터로 53건까지 좁혀짐, 요청 쿼리가 `hasDeadline=true&take=1000&from=…&to=…` 로 나가는 것 확인.

## 1.11 `/calendar` 를 비로그인에 개방 (2026-09-18)

**같은 화면, 소스만 갈린다.** 별도 공개 캘린더를 만들지 않고 `/calendar` 한 화면이 로그인 여부에 따라 데이터 소스를 바꾼다.

| 상태 | 소스 | 화면 |
|---|---|---|
| 비로그인 | `GET /api/public/calendar`(가드 없음, 580건) | 전체 공개 일정 + 대학명 검색 + 로그인 CTA |
| 로그인 | `/matches/me` + `/info-items` + 학교 일정 | 내 일정/전체 토글, 학교 일정 레이어 |

- 두 훅을 동시에 부르되 **한쪽만 실제로 요청**한다(`useCalendarEvents` 는 토큰이 없으면 비활성, `usePublicCalendar` 에 `enabled` 인자를 추가).
- 비로그인 화면에는 내 일정/전체 토글과 학교 일정 블록을 **렌더하지 않는다** — 로그인해야 의미가 생기는 UI다.
- 헤더 네비의 `입시 캘린더` 링크를 로그인 블록 밖으로 빼 모두에게 보이게 했다.
- **검증**: 비로그인 렌더 중 인증 API 호출 0건(모든 `/api/*` 를 401 로 막고 확인).

### 보기 좋게 — 셀을 점에서 색 바로

일정이 580건이라 하루 20건 넘는 날(10.17·10.31·11.28)이 생겼다. 점 3개 + `+n` 으로는 밀도가 읽히지 않는다.

| 요소 | 내용 |
|---|---|
| 카운트다운 | 다가오는 **전 국민 공통 일정**(대학 태그가 없는 것)만 3건, 선두는 브랜드 컬러 큰 카드. 대학별 면접은 사람마다 달라 여기 세우지 않는다 |
| 셀 | 날짜 + 건수 배지 + **카테고리별 색 바**(같은 카테고리는 한 줄로 합침, 최대 3줄 + `+n`) |
| 밀집일 | 5건 이상인 날은 셀 배경을 옅게 칠해 '바쁜 주'가 한눈에 보인다 |
| 지난 날 | 바와 숫자를 흐리게(선택하면 다시 또렷하게) |
| 월 요약 | `23건 · 전형·일정 20 · 마감 3` 스트립 + 하단 색 범례 |
| 정렬 | 하루 안에서 마감 → 학교 시험 → 전형·일정 순으로 색 바를 세운다 |

스타일은 **`design.css` 에 넣는다** — `main.tsx` 가 `styles.css` 다음에 로드하므로 이쪽이 이긴다. 색은 `--brand`·`--ink`·`--muted`·`--line` 토큰을 쓰고, 카테고리 색만 기존 `--c-*` 를 유지한다.

## 2. 데이터 모델 — `ic_info_item` 재활용

**신규 테이블 없음.** 캘린더 이벤트는 기존 정보 아이템에서 **파생**된다.

```
ic_info_item (status=APPROVED)
   └ deadlineAt != null  ──►  CalendarEvent
                              date      = deadlineAt (KST 기준 YYYY-MM-DD)
                              title     = title
                              kind      = category → 색상/아이콘
                              personal  = /matches/me 결과에 포함되면 true
                              reasons   = 매칭 사유 칩 (학년/계열/지역/전형)
```

### 2.1 규칙

| 규칙 | 내용 |
|---|---|
| **일정 판정** | `deadlineAt`이 있는 `APPROVED` 항목만 캘린더에 오른다. 없으면 피드 전용 |
| **날짜 기준** | 저장은 UTC(`timestamptz`), 표시는 **항상 KST**. `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul' })` 로 `YYYY-MM-DD` 산출 (라이브러리 무의존) |
| **개인 일정 판정** | `/matches/me`에 포함 → `personal=true`. 미포함이지만 `/info-items`에 있음 → 공통 일정 |
| **중복 제거** | 두 소스를 `id` 기준 병합, `personal` 우선 |
| **정렬** | 같은 날짜 안에서는 `personal desc → score desc → title asc` |

### 2.2 알려진 한계와 다음 단계

현재 스키마는 **시점(deadlineAt) 하나**만 표현한다. "9/7~9/11 원서접수" 같은 **기간**은 마감일(9/11)로만 찍힌다.

- **Phase 1 (지금)**: 기간 일정은 마감일 기준 1일 이벤트. 본문에 기간 명시.
- **Phase 2 (제안)**: `ic_info_item`에 `event_start_at`, `event_end_at` 두 컬럼 추가(nullable). 기존 데이터 영향 없는 additive 마이그레이션. 캘린더는 `event_start_at ?? deadlineAt` 로 시작일을 잡고 기간 바(bar)를 렌더한다.
- **Phase 3 (제안)**: `ic_user_calendar_pin` — 사용자가 개인 일정(면접일, 자소서 마감 등)을 직접 추가. 이때만 신규 테이블 필요.

┌────────────────────────────────────────────┐

├────────────────────────────────────────────┤

|---|---|
| 개인화 토글 | `내 일정`=`/matches/me` 파생만, `전체`=`/info-items?status=APPROVED` 병합. 기본 `내 일정` |

| 접근성 | 색 점만으로 구분하지 않고 툴팁·상세에 카테고리 라벨 텍스트 병기. 날짜 셀은 `<button>` + `aria-label="9월 7일, 일정 2건"` |

## 4. 화면 B — 대시보드 (`/`) 재구성

요구사항: **여러 섹션 중 입시 캘린더가 가장 주요하게.**

```
┌──────────────────────────────────────────┐
│ ╔══════════════════════════════════════╗ │
│ ║  ⏰  가장 가까운 일정                  ║ │  ← ① 캘린더 히어로 (최상단·최대면적)
│ ║      수시모집 원서접수                 ║ │     · 강조 배경(그라디언트), 화면폭 전체
│ ║          D-18                        ║ │     · D-day를 최대 폰트로
│ ║      9월 7일 (월) · 대교협             ║ │     · 지났으면 "오늘"/"D+n" 처리
│ ║  ─────────────────────────────────  ║ │
│ ║  다음 일정 3건 (D-24 / D-91 / D-113) ║ │     · 후속 일정 미리보기
│ ║  ┌──── 이번 달 미니 캘린더 ────┐      ║ │     · 7×5 소형 그리드, 일정 있는 날 점
│ ║  └────────────────────────────┘      ║ │
│ ║              캘린더 전체 보기 →       ║ │     · /calendar 진입
│ ╚══════════════════════════════════════╝ │
├──────────────────────────────────────────┤
│ ② 내 맞춤 정보  (최근 5건)      전체 보기 →│  ← 기존 피드, 요약 카드로 축소
├──────────────────────────────────────────┤
│ ③ 구독 상태 요약                설정 →    │  ← 채널·빈도·관심태그 한 줄 요약
└──────────────────────────────────────────┘
```

**"가장 주요하게" 를 만드는 4가지 장치**

1. **위치** — 히어로가 첫 화면(above the fold) 전체를 점유. 나머지 섹션은 스크롤 아래.
2. **면적** — 히어로 최소 높이 ≈ 뷰포트 40%, 다른 섹션 카드의 2~3배.
3. **시각 위계** — 유일하게 채색된 블록(브랜드 그라디언트). 나머지는 흰 카드. D-day 숫자는 앱 내 최대 타이포(48px+).
4. **동선** — 히어로 클릭 = `/calendar` 진입. 헤더 네비 첫 항목도 `캘린더`.

**상태별 처리**

| 상태 | 히어로 표시 |
|---|---|
| 비로그인 | 공통 일정(수능/원서접수) D-day + "로그인하면 내 전형 일정만 골라 보여드려요" |
| 로그인·일정 있음 | 위 기본형 |
| 로그인·일정 없음 | "아직 등록된 일정이 없어요" + 구독 설정 유도 |
| 로딩 | 스켈레톤(레이아웃 시프트 방지 — 높이 고정) |

## 5. API 계약 (백엔드 변경 없음)

| 용도 | 호출 | 비고 |
|---|---|---|
| 내 일정 | `GET /matches/me` | 기존. `deadlineAt`, `score`, `reasons` 포함 |
| 전체 일정 | `GET /info-items?status=APPROVED&take=200` | 기존. `enabled: 전체 토글 ON`일 때만 |
| 구독 요약 | `GET /subscriptions/me` | 기존 |

**캐시 정책** — `staleTime` 5분(일정은 자주 안 바뀜), `queryKey: ['calendar', scope]`. 월 이동은 클라이언트 필터링이므로 재요청 없음.

### 5.1 백엔드 개선 제안 (선택, 다음 스프린트)

`take=200` 클라이언트 필터링은 아이템 수백 건까지만 안전하다. 그 이상이면:

```
GET /info-items?from=2026-09-01&to=2026-09-30&hasDeadline=true
```
`QueryInfoItemDto`에 `from`/`to`/`hasDeadline` 3필드 추가 + `InfoItemService.findAll`의 `where.deadlineAt = { gte, lte }`. 30분 작업. **Phase 2 진입 조건: 승인 아이템 300건 초과.**

## 6. 캘린더 ↔ 배달 엔진 연계 (이 앱만 가능한 것)

캘린더는 뷰에 그치지 않고 **발송 트리거의 UI 표현**이 된다.

- **D-7 / D-3 / D-1 자동 리마인더** — 캘린더에 뜬 내 일정은 자동으로 `DEADLINE` 발송 큐에 오른다(Cloud Scheduler 일 1회 스캔). 캘린더에 종 아이콘으로 "알림 예약됨" 표시.
- **역방향 확인** — 푸시로 받은 알림을 캘린더에서 다시 확인(푸시는 휘발, 캘린더는 영구).
- **놓친 일정 회고** — 지난 일정은 흐리게 + "마감됨" 배지. 삭제하지 않는다.
